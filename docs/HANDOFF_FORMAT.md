# HANDOFF 文档格式规范

> 本规范约束 `docs/HANDOFF.md` 的维护方式。**每个开发会话结束前必须按本规范更新
> HANDOFF**；新会话开工时先读本规范 + HANDOFF + ROADMAP，再读任务对应的
> design 文档与提示词。

## 文档总体结构（顺序固定）

1. **文档头**：一句话说明（每会话结束前更新；开工先读本文档 + ROADMAP）
2. **项目一句话**：定位 + GitHub 链接 + License
3. **本机环境**：仓库路径、构建目录、代理、平台限制等
4. **常用命令**：构建、安装、测试、发布 Release
5. **当前进度**：指引节——指向最新会话节号 + ROADMAP，注明会话记录按时间正序
6. **会话记录**：每会话一节，按时间正序；同会话补丁紧跟母节
7. **下一步队列**：按优先级，下一会话从这里开始
8. **架构地图 / 开发约定 / 已知陷阱**：常驻参考节

## 会话节格式

标题：`## 会话 N（YYYY-MM-DD · 一句话主题，版本变化）`

节内条目（无则省略）：

- **交付**：做了什么；commit 短哈希；文件引用相对路径
- **关键实现/坑**：只记「换会话会踩」的——环境陷阱、非直觉根因、语义决定
- **验证**：实测方式与结果、用户验收状态
- **收尾交接**：改了哪些文档哪些节；下一阶段开工提示词路径

## 写作纪律

1. 新会话节追加在会话记录区末尾（正序），常驻节不重排
2. 引用 commit 7 位短哈希；关键改动写清文件+函数名
3. 临时环境必须写清理状态（测试实例、日志重定向进程等）
4. 未完成事项单列（⚠️），写清下一步第一件事——交接核心，宁多勿少
5. 不复制任务书全文：任务书放 `docs/prompts/`，HANDOFF 只放状态和指针
6. 用户反馈定性记录：用户原话诉求 → 实际根因 → 处置结果（防下会话误判）
7. 中文为主，代码/路径/env 名保持原文
